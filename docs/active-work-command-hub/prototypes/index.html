Four ways to ride the Buzz line

Four interactive prototypes for the Active Work board, exploring how far to lean into agenttrail's live-map ideas versus refining the shipped Journey rows + Focus route design. All of them answer the same brief: follow each item's path, see which agents, Buzz threads, and Pi sessions belong to each stage, and dive deeper — with one obvious next action and progressive disclosure everywhere else.

01 Buzz Trail agenttrail itself, pointed at the ticket pipeline — the faithful port
what it is

The open-source board itself, re-pointed: where agenttrail maps a codebase into component cards, this maps the Buzz pipeline — the eight stages are the stable geography across an INTAKE → OPEN / BUILD / PROVE / SHIP world, and your tickets ride through them as task capsules ([~] riding · [!] your gate · [x] cleared, with agent by: chips). The sidebar leads with a ticket selector — click one ticket to see just its journey, ⌘-click to compare several, Overview for everything — above your agent roster and Jira candidates. Now fleshed out with the real harness model: six tickets across both machines, setup states, all four checkpoint states, a done ticket living on as a faded trail — and working behaviors: gate approvals that actually advance the board, a needs-you panel with ack, Pi handoff copy commands, a live buzz.log console, and Ask board answers computed from current state. Both themes, verbatim agenttrail skin.

02 Trail Map the full agenttrail transplant — the pipeline as a place

03 Run Ledger agenttrail's liveness, grafted onto the feed you already scan
what it is

The vertical feed stays, but each journey becomes a live run strip whose signature is the cast ledger — an agents × stages grid where attachment bars show exactly who rode which stage, and when. The live agent carries an observed file line beneath its bar. Every stage column header opens that stage's dossier: Buzz threads with Open in Buzz, Pi sessions with Open pane, the checkpoint record, continuity docs, and the activity log. Needs-you items sit in loud flight strips at the top, each with exactly one action.

Shared foundation

What all three are built on — and why none of them needs backend work.

The harness already knows everything

GET /api/v1/active-work already serves per-stage agents[] (role + link state), buzz_threads[] with buzz:// deep links, pi_sessions[] with pane IDs for /open/pane/…, checkpoint states, and pushes active_work.updated over SSE. These designs are pure presentation.

ADHD-first rules

One obvious priority (needs-you is the only loud thing), progressive disclosure (dossiers on demand, never all at once), calm color (status hues signal state, nothing else), and no dead pixels — everything that looks clickable responds.

Herdr's own skin

Catppuccin Mocha tokens from HerdrTheme.swift, SF Pro / SF Pro Rounded / SF Mono, the same window chrome and sidebar in all three — so options compare on design, not dressing.

agenttrail's transplanted mechanics

Timestamps mutate, structure doesn't (1s t-ago patcher); dash grammar encodes relationship types; declared-vs-observed keeps agents honest; motion runs at two speeds (700ms ambient / 250ms controls) and respects reduced-motion.

The recommendation

Buzz Trail is the chosen direction — Ronnie's call after reviewing the first three: lean all the way into agenttrail rather than borrowing from it. Its practical advantage is real, too: like agenttrail, it's one self-contained web page, so it can ship almost as-is as a harness-served board (a browser tab or a WebView in Herdr) wired to GET /api/v1/active-work + SSE — no SwiftUI rebuild required.

Where the others still earn their keep: Run Ledger's cast-ledger grid remains the best answer to "who was where, when" and could become a zoom altitude or expanded card state inside Buzz Trail; Journey Refit's station popovers are still the cheapest upgrade to the existing native views while the board matures; Trail Map is superseded by Buzz Trail.
